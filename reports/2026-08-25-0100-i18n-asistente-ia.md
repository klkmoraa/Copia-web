# i18n de los mensajes de error/rechazo del Asistente (local) de IA

**Fecha:** 2026-08-25 01:00
**Agente:** Claude Code
**Rama:** claude/propuestas-mejora-rnn8ws

## Qué cambió

El diálogo "Asistente (local)" (`src/features/ai/ProposalAssistant.tsx`) mostraba
en español, sin traducir, todos los mensajes de error/rechazo que produce el
pipeline de `CommandProposalV1` (`src/ai/proposalValidation.ts`,
`proposalCompiler.ts`, `proposalUnits.ts`), aunque el resto del diálogo ya usa
`usePhase2I18n`. Se añadieron ~30 claves nuevas `proposal.error.*` (es/en) en
`src/i18n/phase2Catalogs.ts`, y los tres módulos puros que generaban esos
mensajes pasaron de devolver un string ya resuelto a devolver una clave de
catálogo + parámetros (`key`/`params`), calculando `reason` internamente en
español como antes (para no romper nada que ya dependiera de ese texto). La UI
traduce con `t(outcome.key, outcome.params)` en los tres sitios donde antes
mostraba `outcome.reason` directamente. Los dos mensajes que son texto libre
del proveedor local (`proposal.question`/`proposal.reason` al pedir aclaración
o autorrechazarse) se dejaron sin tocar a propósito: no son plantillas fijas.

## Por qué

Petición del usuario ("propón algo así nuevo", repitiendo el patrón de
"propón mejoras, tienes total permiso de mover lo que quieras"). Era el único
pendiente concreto y verificable que había quedado anotado en
`reports/2026-08-24-1530-mejoras-robustez-ux-y-particion-canvas.md`: "un
usuario en inglés vería los mensajes de error en español dentro del diálogo".
Se descartó tocar el refactor pendiente de `StructuralCanvas.tsx` (despacho
por herramienta + máquina de estados de puntero) en esta misma sesión por su
riesgo alto de acoplamiento; se prefirió un cambio más pequeño y totalmente
verificable.

## Archivos tocados

- `src/i18n/phase2Catalogs.ts` — ~30 claves `proposal.error.*` nuevas en
  `phase2Es`/`phase2En`, con interpolación `{param}`.
- `src/ai/proposalUnits.ts` — `ProposalUnitError` ahora lleva `key`/`params`
  en vez de un `message` ya resuelto; `message` se sigue calculando (en
  español) para quien capture el error como `Error` genérico.
- `src/ai/proposalValidation.ts` — `fail(path, reason)` → `fail(path, key,
  params?)`; `ValidationFailure` gana `key`/`params`. ~19 llamadas migradas.
- `src/ai/proposalCompiler.ts` — `reject(code, reason)` → `reject(code, key,
  params?)`; `PreparationRejected`/`ConfirmationOutcome` ganan `key`/`params`.
  ~11 sitios migrados (incluida una función `rejectConfirmation` nueva para
  los tres rechazos de `confirmProposal`).
- `src/features/ai/ProposalAssistant.tsx` — los tres `setNotice({ ...,
  message: outcome.reason })` pasan a `t(outcome.key, outcome.params)`.
- `src/ai/proposalPipeline.test.ts` — 4 aserciones nuevas sobre `key`/`params`
  en casos ya existentes (allowlist de operación, barra inexistente, sección
  inexistente), sin quitar las aserciones sobre `.reason`.

## Cómo verificar

```bash
npm run typecheck && npm run lint && npm test
npm run verify:docs
npm run build && npm run verify:perf && npm run verify:entry
```

Los siete pasaron limpio (255 archivos de test, 2629 pruebas, 0 advertencias
nuevas de lint; las advertencias que aparecen son preexistentes en archivos
no tocados por este cambio).

Manual sugerido: abrir "Asistente (local)" con el idioma del proyecto en
inglés, pedir un cambio sobre una barra inexistente (p. ej. "aplica IPE200 a
M99") y confirmar que el mensaje de error aparece en inglés.
